# v0.5.1 计划

## 版本目标

`v0.5.1` 聚焦两件事：

1. 继续收敛设备页，把重复的“当前选中设备”详情区移除，统一到设备列表行交互
2. 提升设备识别与设备控制效率，补齐更实用的设备名称展示和当前前台 App 快捷动作

这版 **不纳入** 设备分组筛选、多设备批量操作、网络自动重连、连接诊断、实时 Logcat 工作台等更大块能力，避免范围失控。

## 已确认产品决策

1. `v0.5.1` 范围包含：
   - 移除“当前选中设备”独立区域
   - 将有价值的设备动作统一收口到列表行 `More` 菜单
   - 设备默认显示名称升级为：**别名 > 厂商 + 型号 > 序列号**
   - 列表中继续保留序列号可见性，避免调试时难以精确定位设备
   - 新增“当前前台 App”识别能力
   - 提供前台 App 的强行停止、清除数据、卸载动作
2. 当前设备列表已经具备：
   - 置顶 / 取消置顶
   - 复制序列号
   - 打开设备 Shell
   - 打开最近文件
   - 打开设备日志目录
   - 断开网络设备
3. “当前选中设备”区域移除后，原来仍有价值但尚未迁移的能力，重点是：**设备别名编辑**
4. “清除前台 App 数据”与“卸载前台 App”必须有二次确认；卸载属于高风险动作
5. “当前顶部 App”在文案和交互上统一表述为：**当前前台 App**

## 代码现状判断

当前代码已经具备可复用基础：

- `src/app.rs`
  - 当前设备页仍保留 `ui_selected_device` 区域，且右侧大状态卡在“已选中 / 未选中”两种状态下都会展示
  - 设备列表行的 `More` 菜单已经承载多数高频设备动作，适合继续扩展
  - 当前设备名称展示仍是“别名，否则序列号”
  - 项目已有连接、清理、拖拽目标选择等弹窗模式，可复用到危险动作确认
- `src/models.rs`
  - `DeviceInfo` 当前只有 `serial / state / android_version`
  - 需要扩展设备厂商、型号以及前台 App 相关数据承载方式
- `src/adb.rs`
  - 已有 `list_devices / connect_device / disconnect_device / restart_server / install_apk / push_file / spawn_logcat`
  - 适合继续扩展：
    - 设备厂商 / 型号查询
    - 当前前台 App 解析
    - `am force-stop`
    - `pm clear`
    - `pm uninstall`
- `locales/zh-CN.json` / `locales/en.json`
  - 仍是所有 UI 文案入口，需要同步补齐设备名称、前台 App、危险确认等新文案

结论：**现有结构足够支撑 `v0.5.1`，重点不是重做页面骨架，而是继续消除重复区域、增强列表行菜单和 ADB 设备控制能力。**

## 变更内容

### 1. 移除“当前选中设备”区域

**需求**：
- 当前“当前选中设备”区域里的右侧大卡片信息重复，整体详情区与设备列表存在明显功能重叠
- 设备页需要进一步收敛，减少装饰性占位和重复交互

**方案**：
- 删除设备页中的 `ui_selected_device` 独立区域，而不是只删除右侧视觉卡片
- 保持设备页主结构聚焦为：
  - 顶部概览卡片
  - 动作工具区
  - 设备列表
  - 底部日志输出区
- 若仍需保留“当前设备上下文”，优先保留轻量行选中态，而不是保留整块详情面板

**改动**：

#### `src/app.rs`
- 移除 `ui_selected_device` 在主界面中的渲染入口
- 清理对应布局、状态引用和不再需要的辅助渲染函数
- 确认设备选中态对拖拽目标、状态提示等现有行为的影响

**风险点**：
- 当前部分交互会优先使用“当前选中设备”作为上下文，移除详情区后仍需保留合理的默认目标策略
- 需要避免删除详情区时顺手破坏现有复制、Shell、打开目录等动作的可达性

### 2. 统一设备列表行菜单能力

**需求**：
- 设备页不再依赖独立详情区承载设备操作
- 剩余有效操作应统一进入列表行 `More` 菜单，减少入口分散

**方案**：
- 保留当前列表行的开始 / 停止主动作
- 继续以 `More` 菜单收口扩展能力
- 将“设备别名编辑”迁移到列表行菜单，而不是继续依赖详情区输入框

**改动**：

#### `src/app.rs`
- 审视并整理现有 `More` 菜单项的顺序、分组和启用条件
- 将别名编辑入口迁移到行菜单或配套轻量弹窗
- 清理详情区删除后遗留的别名编辑状态逻辑

**风险点**：
- 若直接把全部动作塞入单层菜单，可能导致菜单过长，需要在实现时注意分组或文案密度

### 3. 设备默认显示名称升级

**需求**：
- 当前默认把序列号当作主显示名称，可读性偏弱
- 理论上可以从设备拿到厂商和型号，更适合作为默认展示名

**方案**：
- 补充设备元数据采集：
  - `ro.product.manufacturer`
  - `ro.product.model`
- 统一显示规则：
  - 优先显示别名
  - 否则显示“厂商 + 型号”
  - 无法获取时回退序列号
- 列表中继续展示序列号作为次级信息，兼顾可读性和可定位性

**改动**：

#### `src/models.rs`
- 扩展 `DeviceInfo` 结构，增加厂商 / 型号字段

#### `src/adb.rs`
- 在设备枚举或设备详情查询阶段补充厂商 / 型号读取
- 对读取失败、空值和异常输出做稳妥回退

#### `src/app.rs`
- 升级设备主名称和身份文案拼装逻辑
- 统一列表、状态提示、下拉选择中的设备名称展示

**测试**：
- 设备名在“有别名 / 无别名 / 无法读取厂商型号”三种场景下回退正确
- 多设备列表中仍能清晰区分同型号设备

### 4. 当前前台 App 识别与快捷动作

**需求**：
- 需要从设备列表直接对“当前前台 App”做常用处理，减少切去终端手敲 adb 命令
- 覆盖高频问题定位和调试动作：强停、清数据、卸载

**方案**：
- 在设备列表行 `More` 菜单中新增“当前前台 App”入口或分组
- 先识别当前前台包名 / Activity，再基于识别结果提供动作
- 解析时做多种 Android 输出格式兜底，不依赖单一 `dumpsys` 输出

**改动**：

#### `src/adb.rs`
- 新增当前前台 App 查询能力
- 优先从 `dumpsys activity` / `dumpsys window` 等输出解析当前前台组件
- 新增：
  - `am force-stop <package>`
  - `pm clear <package>`
  - `pm uninstall <package>`
  的封装与输出整理

#### `src/models.rs`
- 如有必要，新增前台 App 查询 / 动作结果对应的事件数据结构

#### `src/app.rs`
- 在列表行菜单中增加前台 App 查询和动作入口
- 展示当前前台 App 包名，必要时补充 Activity 信息
- 处理执行中状态、成功反馈和失败反馈

**风险点**：
- 不同 Android 版本 / ROM 的 `dumpsys` 输出格式可能不同，解析逻辑需要分层兜底
- 前台 App 可能为空、系统桌面、系统设置或瞬时切换，UI 和状态提示要考虑这些边界

### 5. 危险操作确认与提示

**需求**：
- “清除数据”“卸载”都属于高风险动作，不能做成无确认的一键执行

**方案**：
- 复用项目现有弹窗模式新增确认对话框
- 确认框中明确显示：
  - 目标设备
  - 目标包名
  - 即将执行的动作
  - 动作是否可逆
- 卸载动作在视觉上应与普通操作区分

**改动**：

#### `src/app.rs`
- 增加前台 App 危险动作确认弹窗
- 管理确认中的临时状态和执行后的 UI 刷新

#### `locales/*.json`
- 补齐确认标题、动作说明、错误反馈、成功提示等文案

**测试**：
- 清除数据 / 卸载未确认时不会执行
- 确认后能对正确设备、正确包名执行动作
- 操作失败时能展示可读错误，而不是静默失败

## 推荐实施顺序

1. **先做设备名称升级**
   - 扩展厂商 / 型号元数据
   - 把展示规则统一成“别名 > 厂商 + 型号 > 序列号”
2. **再移除“当前选中设备”区域**
   - 清理重复布局
   - 保住行选中态和现有上下文逻辑
3. **再把别名编辑迁到列表行菜单**
   - 避免移除详情区后丢失唯一剩余有效能力
4. **然后接入前台 App 识别**
   - 先把“识别谁是当前前台 App”做稳，再接动作
5. **最后补前台 App 危险动作与确认**
   - 强停 / 清数据 / 卸载
   - 统一收口状态提示、中英文文案和验证

- 设备页移除“当前选中设备”区域后，列表主流程仍可正常完成设备操作

- 新增状态提示、菜单文案、确认弹窗保持中英文同步
