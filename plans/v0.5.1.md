# v0.5.1 计划

> **状态：已完成。** `v0.5.1` 已完成设备页收敛、设备名称升级、前台 App 快捷动作、同机 USB / Wi‑Fi 聚合与 Windows 包构建；设备列表右侧留白已做收口，当前最终实现仍有轻微视觉不完全一致，但按可接受状态收口。

## 版本目标

`v0.5.1` 聚焦两件事：

1. 继续收敛设备页，把重复的“当前选中设备”详情区移除，统一到设备列表行交互
2. 提升设备识别与设备控制效率，补齐更实用的设备名称展示和当前前台 App 快捷动作

这版 **不纳入** 设备分组筛选、多设备批量操作、网络自动重连、连接诊断、实时 Logcat 工作台等更大块能力，避免范围失控。

## 已确认产品决策

1. `v0.5.1` 范围包含：
   - 移除“当前选中设备”独立区域
   - 将有价值的设备动作统一收口到列表行 `More` 菜单
   - 设备默认显示名称升级为：**别名 > 厂商 + 型号 > 序列号**
   - 将同一物理设备的 USB / Wi‑Fi ADB 连接映射为同一设备
   - 当同一设备同时存在 USB 和 Wi‑Fi transport 时，优先使用 USB
   - 列表中继续保留序列号可见性，避免调试时难以精确定位设备
   - 新增“当前前台 App”识别能力
   - 提供前台 App 的强行停止、清除数据、卸载动作
2. 当前设备列表已经具备：
   - 置顶 / 取消置顶
   - 复制序列号
   - 打开设备 Shell
   - 打开最近文件
   - 打开设备日志目录
   - 断开网络设备
3. “当前选中设备”区域移除后，原来仍有价值但尚未迁移的能力，重点是：**设备别名编辑**
4. “清除前台 App 数据”与“卸载前台 App”必须有二次确认；卸载属于高风险动作
5. “当前顶部 App”在文案和交互上统一表述为：**当前前台 App**

## 最终实现概况

最终代码已按 `v0.5.1` 目标完成收口：

- `src/app.rs`
  - 已移除设备页 `ui_selected_device` 独立区域，设备页主体聚焦为概览卡片、动作区、设备列表和底部状态区
  - 设备列表行 `More` 菜单已承载别名编辑、复制序列号、打开 Shell、打开日志目录、前台 App 动作等能力
  - 设备展示、选择、置顶、拖拽目标与日志目录归属已切换为“物理设备身份优先”
  - 设备页右侧留白已做收口，不会再出现明显贴边；但空态与非空态下仍有轻微视觉差异，当前按已接受状态保留
- `src/models.rs`
  - `DeviceInfo` 已扩展为 `serial / identity_key / manufacturer / model / state / android_version`
  - 已增加 `transport_serials`、前台 App 数据结构与相关异步事件
- `src/adb.rs`
  - 已补齐设备厂商 / 型号查询、物理设备 identity 查询、当前前台 App 解析
  - 已补齐 `am force-stop`、`pm clear`、`pm uninstall` 封装
- `locales/zh-CN.json` / `locales/en.json`
  - 已同步补齐别名弹窗、前台 App 动作、危险确认、状态提示等双语文案
- `README*` / `CHANGELOG*` / `Cargo.toml`
  - 已同步收口版本号、说明文档与发布记录

结论：**`v0.5.1` 最终没有重做页面骨架，而是在现有结构上完成设备页收敛、设备身份升级和高频控制能力补齐。**

## 变更内容

### 1. 移除“当前选中设备”区域

**需求**：
- 当前“当前选中设备”区域里的右侧大卡片信息重复，整体详情区与设备列表存在明显功能重叠
- 设备页需要进一步收敛，减少装饰性占位和重复交互

**方案**：
- 删除设备页中的 `ui_selected_device` 独立区域，而不是只删除右侧视觉卡片
- 保持设备页主结构聚焦为：
  - 顶部概览卡片
  - 动作工具区
  - 设备列表
  - 底部日志输出区
- 若仍需保留“当前设备上下文”，优先保留轻量行选中态，而不是保留整块详情面板

**最终实现**：
- 已完整移除独立详情区
- 设备行选中态继续保留，用于拖拽目标与设备上下文
- 原详情区承载的有效能力已迁回列表行菜单和弹窗

**改动**：

#### `src/app.rs`
- 移除 `ui_selected_device` 在主界面中的渲染入口
- 清理对应布局、状态引用和不再需要的辅助渲染函数
- 确认设备选中态对拖拽目标、状态提示等现有行为的影响

**风险点**：
- 当前部分交互会优先使用“当前选中设备”作为上下文，移除详情区后仍需保留合理的默认目标策略
- 需要避免删除详情区时顺手破坏现有复制、Shell、打开目录等动作的可达性

### 2. 统一设备列表行菜单能力

**需求**：
- 设备页不再依赖独立详情区承载设备操作
- 剩余有效操作应统一进入列表行 `More` 菜单，减少入口分散

**方案**：
- 保留当前列表行的开始 / 停止主动作
- 继续以 `More` 菜单收口扩展能力
- 将“设备别名编辑”迁移到列表行菜单，而不是继续依赖详情区输入框

**最终实现**：
- 列表行继续保留开始 / 停止主动作
- `More` 菜单已统一承载置顶、别名编辑、复制序列号、Shell、打开输出、打开设备日志目录、断开网络设备等入口
- 别名编辑已改为从列表行菜单打开独立对话框

**改动**：

#### `src/app.rs`
- 审视并整理现有 `More` 菜单项的顺序、分组和启用条件
- 将别名编辑入口迁移到行菜单或配套轻量弹窗
- 清理详情区删除后遗留的别名编辑状态逻辑

**风险点**：
- 若直接把全部动作塞入单层菜单，可能导致菜单过长，需要在实现时注意分组或文案密度

### 3. 设备默认显示名称升级

**需求**：
- 当前默认把序列号当作主显示名称，可读性偏弱
- 理论上可以从设备拿到厂商和型号，更适合作为默认展示名

**方案**：
- 补充设备元数据采集：
  - `ro.product.manufacturer`
  - `ro.product.model`
- 统一显示规则：
  - 优先显示别名
  - 否则显示“厂商 + 型号”
  - 无法获取时回退序列号
- 列表中继续展示序列号作为次级信息，兼顾可读性和可定位性

**最终实现**：
- 已补充厂商 / 型号采集
- 最终显示规则为：**别名 > 厂商 + 型号 > 序列号**
- 若型号已包含厂商，则自动去重显示
- 列表行继续显示原始序列号作为次级信息，便于外部 adb 协同

**改动**：

#### `src/models.rs`
- 扩展 `DeviceInfo` 结构，增加厂商 / 型号字段

#### `src/adb.rs`
- 在设备枚举或设备详情查询阶段补充厂商 / 型号读取
- 对读取失败、空值和异常输出做稳妥回退

#### `src/app.rs`
- 升级设备主名称和身份文案拼装逻辑
- 统一列表、状态提示、下拉选择中的设备名称展示

**测试**：
- 设备名在“有别名 / 无别名 / 无法读取厂商型号”三种场景下回退正确
- 多设备列表中仍能清晰区分同型号设备

### 4. 当前前台 App 识别与快捷动作

**需求**：
- 需要从设备列表直接对“当前前台 App”做常用处理，减少切去终端手敲 adb 命令
- 覆盖高频问题定位和调试动作：强停、清数据、卸载

**方案**：
- 在设备列表行 `More` 菜单中新增“当前前台 App”入口或分组
- 先识别当前前台包名 / Activity，再基于识别结果提供动作
- 解析时做多种 Android 输出格式兜底，不依赖单一 `dumpsys` 输出

**最终实现**：
- 已接入当前前台 App 查询、包名 / Activity 展示
- 识别优先走 `dumpsys activity`，失败时回退 `dumpsys window`
- 已支持查看、强行停止、清除数据、卸载当前前台 App
- 动作执行过程具备进行中状态和结果反馈

**改动**：

#### `src/adb.rs`
- 新增当前前台 App 查询能力
- 优先从 `dumpsys activity` / `dumpsys window` 等输出解析当前前台组件
- 新增：
  - `am force-stop <package>`
  - `pm clear <package>`
  - `pm uninstall <package>`
  的封装与输出整理

#### `src/models.rs`
- 如有必要，新增前台 App 查询 / 动作结果对应的事件数据结构

#### `src/app.rs`
- 在列表行菜单中增加前台 App 查询和动作入口
- 展示当前前台 App 包名，必要时补充 Activity 信息
- 处理执行中状态、成功反馈和失败反馈

**风险点**：
- 不同 Android 版本 / ROM 的 `dumpsys` 输出格式可能不同，解析逻辑需要分层兜底
- 前台 App 可能为空、系统桌面、系统设置或瞬时切换，UI 和状态提示要考虑这些边界

### 5. 危险操作确认与提示

**需求**：
- “清除数据”“卸载”都属于高风险动作，不能做成无确认的一键执行

**方案**：
- 复用项目现有弹窗模式新增确认对话框
- 确认框中明确显示：
  - 目标设备
  - 目标包名
  - 即将执行的动作
  - 动作是否可逆
- 卸载动作在视觉上应与普通操作区分

**最终实现**：
- “清除前台 App 数据”与“卸载前台 App”均已接入确认弹窗
- 确认内容会展示目标设备、目标 App 和对应动作
- 未确认不会执行，失败时会展示明确错误

**改动**：

#### `src/app.rs`
- 增加前台 App 危险动作确认弹窗
- 管理确认中的临时状态和执行后的 UI 刷新

#### `locales/*.json`
- 补齐确认标题、动作说明、错误反馈、成功提示等文案

**测试**：
- 清除数据 / 卸载未确认时不会执行
- 确认后能对正确设备、正确包名执行动作
- 操作失败时能展示可读错误，而不是静默失败

### 6. 同一物理设备的 USB / Wi‑Fi 聚合

**需求**：
- 同一台设备通过 USB 与 Wi‑Fi 同时连入时，不应在 UI 和配置层被当作两个完全无关的设备
- 别名、置顶、日志目录、拖拽目标等能力需要绑定到“物理设备”而不是瞬时 transport

**方案**：
- 从设备查询稳定 identity，优先使用 `ro.serialno`，回退 `ro.boot.serialno`
- 按物理 identity 合并多条 transport 记录
- 当同机同时存在 USB 与 Wi‑Fi transport 时，优先使用 USB 作为主 transport

**最终实现**：
- 已按 identity 合并同一物理设备的 USB / Wi‑Fi 连接
- 配置归属、列表展示、日志目录与选择逻辑都已切换到 identity 维度
- 主 transport 已实现“可用优先、同等可用时 USB 优先”
- Wi‑Fi 断开动作仍会优先命中网络 transport

### 7. 设备页右侧留白收口

**需求**：
- 设备页在有无竖向滚动条两种情况下，设备列表大卡片都不应出现明显贴右边缘的问题

**方案**：
- 基于 `ScrollArea` 视口信息判断当前是否出现竖向滚动条
- 仅对设备列表卡片宽度和右侧 gutter 做收口，避免影响上方概览区与操作区宽度

**最终实现**：
- 已避免设备列表卡片在无滚动条时直接贴右边缘
- 最终实现重点保证“不贴边”和整体观感稳定
- 空态与非空态下的右侧间距仍存在轻微视觉不完全一致，当前版本按可接受状态收口，后续如需继续追求像素级一致可再单独处理

**改动**：

#### `src/app.rs`
- 基于 `ScrollArea::show_viewport` 判断设备页是否出现竖向滚动条
- 将右侧 gutter 收敛到设备列表卡片自身，避免整个主内容区被一并压窄

**测试**：
- `content_view_width` 已补充边界测试，保证预留 gutter 时不会出现负宽度
- 已结合 `cargo fmt` / `cargo test` / `cargo check` 与打包流程做整体验证

## 实际实施顺序

1. **先完成设备名称与数据模型升级**
   - 扩展厂商 / 型号 / identity 元数据
   - 统一展示规则为“别名 > 厂商 + 型号 > 序列号”
2. **再收敛设备页结构**
   - 移除“当前选中设备”区域
   - 把别名编辑迁到列表行菜单和弹窗
3. **然后补齐前台 App 识别与动作**
   - 先把识别做稳，再接强停 / 清数据 / 卸载
4. **再完成同机 USB / Wi‑Fi 聚合**
   - 统一物理设备 identity
   - 收口别名、置顶、日志目录和 transport 优先级
5. **最后做文档、验证与布局收口**
   - README / CHANGELOG 双语同步
   - `cargo fmt` / `cargo test` / `cargo check`
   - Windows EXE / zip 打包
   - 设备页右侧留白收口
